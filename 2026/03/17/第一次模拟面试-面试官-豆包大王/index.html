第一次模拟面试

Java基础和JUC/JVM

你提到掌握 ArrayList 和 HashMap 的底层结构，请问HashMap JDK1.7 和 JDK1.8 的核心区别有哪些？为什么 JDK1.8 要引入红黑树？
  • 我的回答: JDK1.8在链表过长时,会将链表转化为红黑树,这样可以显著提升查询效率
  • 标准一点的回答(三个维度):
    1. 为什么要替换?链表的性能瓶颈,链表查询的时间复杂度时O(n),当哈希分布不均匀的时候(Hash函数设计不合理或者Hash扩容不及时或者一些极端情况),链表会变得很长,造成查询效率显著降低;而一旦利用了红黑树,时间复杂度可以降低到O(logN),可见红黑树性能优势更大;
    2. 触发条件是什么?链表长度>=8&&哈希表容量>=64链表会变成红黑树,而红黑树节点<=6才会回转成链表(防止链表和红黑树频繁转换带来的性能开销);
    3. 为什么选红黑树而不是别的树如平衡二叉树?在查询效率上他们都是O(logN),但是红黑树是弱平衡二叉树,它只要求左右子树高度相差不超过两倍即可,相比于别的强二叉树,在频繁插入删除的前提下,旋转次数更少,性能开销也就更少.
JDK1.7 的 ConcurrentHashMap 用了分段锁（Segment）保证线程安全，而 JDK1.8 做了大幅调整，请问：JDK1.8 中 ConcurrentHashMap 的核心加锁机制是什么？相比 JDK1.7 的分段锁，这种新机制有哪些优势？除了核心加锁逻辑，JDK1.8 还做了哪些优化来提升 ConcurrentHashMap 的性能？

  • 我的回答: JDK1.8利用了,synchronized的字段实现了单节点的锁,同时利用volatile提升可见性防止读缓存,Segment分段锁是正对于哈希表的某一个范围的锁,锁的粒度大,影响吞吐量

  • 标准一点的回答:

    1. JDK1.8的ConcurrentHashMap的核心加锁机制:(1).基础加锁: 对哈希表中的头节点加synchronized(锁粒度小到单个桶),只有多个线程操作同一个桶才会有锁的竞争;(2)CAS+自旋优化: 对于节点的插图和值替换,会优先进行CAS操作,CAS失败说明这个锁有竞争后才会进行加锁;(3)可见性保证:对于Node节点的val和next,使用volatile修饰,这样一个线程修改,其他线程就可以立马看到,可以避免读缓存;

    2. 相比于JDK1.7的优势:Segment 是 ConcurrentHashMap 的内部类，每个 Segment 对应一个子哈希表（默认 16 个 Segment），对 Segment 加锁相当于锁住一整组桶，即使线程操作的是同一 Segment 内的不同桶，也会产生锁竞争；(1)1.8版本的锁粒度明显更小，不同桶的操作完全无锁竞争，高并发下吞吐量大幅提升;(2)synchronized 经过 JVM 优化（偏向锁、轻量级锁、重量级锁升级）,性能已经接近于ReentrantLock,同时还有CAS优化;(3)读操作再volatile的修饰下无需加锁;

    3. 做法: 上面那种红黑树的优化;取消segment使用粒度更低的Synchronized修饰头节点;读操作无锁化

在 Java 并发编程中，synchronized 和 ReentrantLock 都是实现线程同步的核心方式，且二者都支持可重入：从功能特性、使用方式、底层实现三个维度，说说它们的核心区别有哪些？实际开发中（比如订单扣库存、秒杀接口限流等场景），你会如何选择使用 synchronized 还是 ReentrantLock？请举例说明。ReentrantLock 的 “公平锁 / 非公平锁” 是什么意思？默认是哪种？实际场景中为什么很少用公平锁？
  • 我的回答:synchronized和ReentrantLock都是可重入的锁,前者可以通过修饰函数或者包裹代码端自动加锁和解锁,但是后者要手动加锁和释放,synchronized是不公平的,但是后者可以设置公平锁也可以设置非公平锁,同时前者如果获取不了锁会一直竞争,但是后者可以中断,底层的话,前者是基于java每个对象都有一个monitor对象,可以通过它来上锁,后者是AQS框架的实现,主要利用了一个计数器来检测锁是否被占用,实际开发中介于分布式使用了redis的锁,公平锁就是让队列按顺序获取锁,所释放只会唤醒队头的线程,但是非公平锁则是唤醒所有线程让他们抢占,公平锁之所以用的少因为这种谁需按照顺序可能因为一个线程慢了而影响后续的所有线程
  • 标准一点的回答:
    1. 区别:
      • 功能特性:synchronized不支持中断和超时等待,仅支持非公平锁,无额外高级功能;但是ReentrantLock 支持可中断等待(lockInterruptibly()),超时等待(tryLock (time)),尝试获取锁(tryLock()),支持公平锁 / 非公平锁(构造方法指定), 支持条件变量(Condition),可分组唤醒线程;
      • 使用方式:synchronized修饰方法/代码块,自动加锁/释放(异常也会自动释放);语法简洁,无手动操作成本;ReentrantLock必须手动调用lock()加锁unlock()释放(需在 finally 块中释放,避免异常导致死锁);语法灵活,但有手动操作成本;
      • 底层实现:synchronized是JVM层面的内置锁(监视器锁),基于对象的对象头(Monitor)来实现,JDK1.6以后优化了“偏向锁->轻量级锁->重量级锁”的升级机制;而ReentrantLock是JDK中API层面的,基于AQS框架实现,AQS核心是一个双向链表等待队列和一个volatile修饰的state(重入次数)实现,纯java代码实现;
    2. 选用原则:
      • synchronized使用场景:简单的同步场景(单例初始化,普通方法同步);高并发但相对来说没那么激烈(例如缓存重构或缓存构建时防止多用户同时进行缓存用这个就好了);
      • ReentrantLock使用场景:需要中断或者超时等待的场景(下单接口可以设置tryLock(3,TimeUnit.SECONDS)防止用户等待时间过长影响体验);那种排队场景需要使用公平锁;生产者消费者模型这种需要唤醒对方也需要用这个锁;
    3. ReentrantLock 的公平锁 / 非公平锁:
      • 公平锁:按照申请锁的顺序来进行锁获取,每次只会唤醒队头的
      • 非公平锁:唤醒依就是唤醒队头的线程,但是新来的线程可以直接进行CAS枪锁,如果锁被别人持有就会进入AQS队列
      • 实际场景中为什么很少用公平锁？公平锁性能损耗大,它需要频繁的检查队列,而非公平锁在CAS枪锁成功是不需要检查队列;同时往往实际场景如“秒杀”无需绝对的公平,毕竟毫秒级只差用户也无知觉,但非公平却能一定程度的提高吞吐量(注意:但是非公平锁可能会出现高频的新线程,造成队列后面的线程一直抢不到锁,导致“线程饥饿”)
JVM 内存模型（JMM）是解决多线程可见性、原子性、有序性问题的核心，请问：首先用通俗的语言解释：什么是 JMM？主存和工作内存的关系是什么？JMM 定义了主存与工作内存之间的 8 种交互操作（lock/unlock/read/load 等），核心的交互规则有哪些？（不用记全 8 种，说核心规则即可）volatile 关键字是 Java 并发中保证可见性和有序性的关键，它具体是如何保证可见性的？又是如何禁止指令重排的？补充追问：volatile 能保证原子性吗？比如volatile int i = 0; i++是线程安全的吗？为什么？

  • 我的回答: 不会

  • 标准一点的回答:

    1. JMM: JMM不是实际的物理内存结构,而是JVM定义的一套规则,用于规划多线程如何访问共享数据,解决了多线程下的可见性,原子性和有序性;

    2. 主存和工作内存:主存相当于一个公共的仓库,存储着线程共享的变量(实例变量, 静态变量);而工作内存相当于每个每个线程的私人工作台,线程要操作共享变量,不能直接修改主存,必须要把变量拷贝到自己的工作内存,修改后再写回主存;多线程的工作内存相互隔离,线程 A 修改了变量但没写回主存,线程 B 就看不到,这就是可见性问题;线程执行时指令乱序,就是有序性问题

    3. 8种交互操作(只详细写核心的3个):

      • 只读不写:线程读取共享变量时，必须先把主存的最新值加载到工作内存，不能直接用工作内存的旧值
      • 只写不读:线程修改共享变量后，必须立刻把工作内存的新值写回主存，不能只改工作内存不写回
      • 互斥操作:对主存中变量的lock(锁定)和unlock(解锁)操作必须成对出现,且一个变量同一时间只能被一个线程锁定

    4. volatile 如何保证可见性和禁止指令重排:

      • 可见性: 线程修改volatile修饰的数据,立马刷新回主存(强制写回);其他线程读取该变量,立刻丢弃工作线程的旧值,去主存读取最新值(强制刷新);做到了变量的修改对所有线程可见

      • 禁止指令重排: volatile会给变量添加内存屏障,内存屏障可以阻止指令重排,也可以强制cpu刷新缓存

    5. volatile不可以保证原子性

JVM 的垃圾收集器是性能调优的核心，JDK1.8 中默认的垃圾收集器是 G1（部分版本默认 Parallel Scavenge + Parallel Old），请回答：请分别简述 Serial、Parallel（并行）、CMS、G1 这 4 种垃圾收集器的核心特点和适用场景；CMS 收集器的 “标记 - 清除” 算法会带来什么问题？G1 是如何解决这些问题的？实际开发中（比如电商秒杀、后台管理系统），你会如何选择垃圾收集器？请举例说明。
